# Ecommerce Tracking Auditor

Run a real browser journey from an ecommerce homepage through product, cart and checkout initiation. The auditor records browser-side analytics requests and dataLayer activity, then creates CSV, JSON, screenshots and a local HTML report. It never fills checkout fields or places an order.

## Output

- `report.html`: self-contained report layout that opens in any browser
- `summary.csv`: expected GA4 and Meta events with `passed`, `failed`, `not_configured` or `not_tested` status
- `tracking_requests.csv`: recognized browser requests with sensitive personal parameters redacted
- `data_layer.csv`: dataLayer pushes captured on each reached page
- `journey.json`: complete structured evidence
- PNG screenshots for each reached journey stage

The HTML is generated by a fixed Python template after the audit. It does not require AI or a web server.

## Install and run

```powershell
py -3 -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -e .
python -m playwright install chromium
ecommerce-tracking-auditor
```

Paste the store homepage when prompted, or use arguments:

```powershell
ecommerce-tracking-auditor https://example-store.com --headed
```

When launched without arguments (including by double-clicking the Windows executable), the completed HTML report opens automatically and the terminal remains open until you press Enter.

If automatic product discovery fails:

```powershell
ecommerce-tracking-auditor https://example-store.com --product https://example-store.com/product/example/
```

## Build a Windows executable

```powershell
.\build_exe.ps1
```

The executable first uses Playwright Chromium when it is installed, then tries an installed Google Chrome or Microsoft Edge browser. Bundling a browser into the executable would add hundreds of megabytes and complicate browser security updates.

After publishing to GitHub, the `build-windows` Actions workflow can also build a downloadable Windows executable artifact on demand.

## How results are interpreted

- `passed`: the journey stage was reached and the expected request was observed
- `failed`: the stage was reached, the provider was active, and the expected request was not observed
- `not_configured`: the stage was reached but no requests from that provider were observed
- `not_tested`: the tool did not reach the stage, so it makes no claim about that event

This distinction prevents an incomplete cart journey from being reported as six confirmed tracking defects.


## Scope and limitations

- Version 0.1 uses common WooCommerce and general storefront selectors. Some themes, headless stores, iframes and custom carts require a supplied product URL or new selectors.
- The audit covers browser-side signals only. It does not validate server-side events or whether a vendor accepted and attributed an event.
- It stops at the checkout page and does not test `purchase`.
- Consent behaviour varies by region and platform. The report records what the automated browser observed in that run.
- Run it only on stores you own or are authorized to test.
